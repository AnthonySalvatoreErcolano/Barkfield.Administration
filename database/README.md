# Database

Hand-written SQL for **Azure SQL Database** (SQL Server). There is no ORM and no
migration tool — the project uses Dapper with hand-written SQL, so schema changes are
numbered scripts applied in order.

## Applying

```bash
sqlcmd -S <server> -d <database> -U <user> -P <password> -I -i migrations/001_initial_schema.sql
sqlcmd -S <server> -d <database> -U <user> -P <password> -I -i migrations/002_seed_reference_data.sql
```

Run them in numeric order. `001` creates everything and assumes an empty database.
`002` is idempotent and safe to re-run.

### ⚠️ `-I` is not optional

The schema uses **filtered indexes**, which require `QUOTED_IDENTIFIER ON` — not only
to create them, but for **any insert, update or delete** on the tables that carry them.

`sqlcmd` defaults that setting to **OFF**, so without `-I` you get:

> Msg 1934 — DELETE failed because the following SET options have incorrect settings:
> 'QUOTED_IDENTIFIER'

The scripts set it themselves at the top, so applying them works either way. It is
**ad-hoc DML afterwards** that bites. Both scripts have been applied and exercised
against SQL Server LocalDB, including this case.

This does not affect the application: .NET `SqlClient` sets `QUOTED_IDENTIFIER ON` by
default, as do SSMS and Azure Data Studio. It is a `sqlcmd` quirk.

## Adding a migration

Next number, never edit an applied script. Name it `NNN_short_description.sql`.
Write it to be re-runnable where that is cheap (guarded inserts, `IF NOT EXISTS`),
because it removes a whole class of deployment mistake.

## Creating the first user

Nothing seeds a login — a script shipping a known password hash is a liability the
moment it reaches production. Use the bootstrap command instead:

```bash
cd Barkfield.Administration.API
dotnet run -- create-admin --email you@barkfieldroad.com --name "Your Name"
```

It prompts for the password without echoing it, so the password never lands in shell
history. Pass `--password "..."` to supply it non-interactively for scripted setup.

It reads the same `ConnectionStrings:ConnectionString` the API uses, hashes through the
same `IPasswordHasher` the sign-in path uses, refuses a duplicate email or a password
under 12 characters, and grants the Administrator role.

**Do not write this INSERT by hand.** `PasswordHash` holds a BCrypt hash at work factor
12, which T-SQL cannot produce — hand-written SQL means generating the hash somewhere
else and hoping the work factor matches. The command exists so that cannot drift.

## Conventions

| | |
|---|---|
| Surrogate keys | `UNIQUEIDENTIFIER`, generated by the **application**, never `NEWID()` defaults — the domain's `Create()` factories assign ids |
| Enums | `TINYINT` + a `CHECK` constraint listing valid values. **Update the constraint when the C# enum gains a member** |
| Money | `DECIMAL(10,2)` |
| Coordinates | `DECIMAL(9,6)` |
| Timestamps | `DATETIME2(3)`, always UTC |
| Calendar dates | `DATE` |
| Time-of-day | `TIME(0)` |
| Text | `NVARCHAR` throughout |

**Value objects are flattened.** `Address` becomes `Street` / `City` / `State` /
`ZipCode`, `TimeWindow` becomes `*Start` / `*End`, `GeoPoint` becomes
`*Latitude` / `*Longitude`. The `FromDto` factories on each entity reassemble them.

**Cascades stay inside an aggregate.** Anything crossing an aggregate boundary is
`NO ACTION` — partly to preserve history, partly because SQL Server refuses multiple
cascade paths to the same table. A practical consequence: **a customer with delivery
history cannot be deleted**, because `Deliveries` holds a `NO ACTION` reference. That
is intended. Customers should be deactivated, not deleted.

## Things worth knowing

**`dbo.UserPermissions` is a view**, not a table. It flattens
user → role → permission for `PermissionAuthorizationFilter`, which checks a permission
name against a user id on every guarded request (cached 5 minutes). `Users.IsAdmin` is
the escape hatch that filter also honours.

**`DeliveryLines.SourceId` is deliberately not a foreign key.** It points at a
`SubscriptionItem`, a `RotationGroup` or a `SubscriptionAddOn` depending on `Source`,
and the row it names may be edited or removed long after the delivery is history.

**`Deliveries.ProcurementStatus` is derived but stored.** The `Delivery` aggregate
recomputes it on every line change. It is persisted so the packing worklist can filter
on it in SQL — and because the aggregate owns the only write path to its lines, the
stored value cannot drift from what it summarises.

**`WebhookEvents` is the idempotency table.** The routing provider retries any webhook
it does not get a 200 for, and events arrive out of order. Handlers record the
provider's event id before doing anything and skip what is already there.

**Snapshots are intentional duplication.** `DeliveryLines` copies product name and unit
price, and `Deliveries` copies the delivery address, both captured at scheduling time.
Repricing a product or a customer moving house must never rewrite what a past delivery
shipped, charged, or went to.

## Known trade-offs

**GUID clustered primary keys.** Random GUIDs as clustered keys fragment indexes over
time. At this scale — a few hundred customers and roughly 4,000 deliveries a year —
it makes no practical difference, and the alternatives (sequential GUIDs, or a separate
`BIGINT` clustering key) add complexity for no gain. Revisit only if a table passes a
few million rows.

**`AuditLogs.Timestamp`** uses a column name that shadows a SQL Server type keyword.
It is legal, and it matches the `INSERT` already written in `SqlExecutor.ExecuteWithAudit`,
so it stays as-is.

**`TimeOnly` needs a Dapper type handler, and the application registers one.** Dapper
2.1.79 reads a `TIME` into a `TimeOnly` happily but refuses to send one back as a
parameter — *"cannot be used as a parameter value"*. So every write touching a time
window fails at runtime while the read path looks perfectly healthy, which is exactly how
it was found. `DapperTypeHandlers` covers both directions and is registered from
`SqlExecutor`'s static constructor so it cannot be bypassed. Don't work around it per
call site.

**`DateTime` parameters arrive as `DATETIME`, not `DATETIME2`.** SqlClient infers
`SqlDbType.DateTime` for a .NET `DateTime`, and that type's granularity is ~3.33 ms — so a
value read out of a `DATETIME2(3)` column does **not** compare equal to itself when sent
straight back. Range comparisons and `DATE` columns are unaffected; equality on a
timestamp is not. That is why `Subscriptions.Revision` exists instead of an
`UpdatedAt` concurrency check.
